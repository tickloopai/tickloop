# Tickloop

Tickloop (tickloop.ai) is a terminal AI agent for code and office work: the `tickloop` command starts the agent, and Tickhost runs every local Tick. This repository is a domain-agnostic host: it knows no Tick kinds, domain concepts or specific package programs. Official Tick packages (programs, manifests and Skills) and their releases live in [tickloopai/ticks](https://github.com/tickloopai/ticks); this repository keeps only the plugin mechanism. Accepting a host integration never requires a real data-source account.

- Terms follow [CONTEXT.md](./CONTEXT.md); use its names in code, UI and discussion. Internal module boundaries are not product Tick types.
- When a change conflicts with documented behavior, say so; never change a meaning silently. When documents and source disagree, the source wins.
- Division of documents: agent instructions live only in AGENTS.md (no CLAUDE.md); CONTEXT.md holds term definitions only; user-facing usage lives in `README.md`, `README.zh-CN.md` and `docs/` (`docs/zh-CN/` mirrors it).

## Core behavior

- **Tick Instance**: each run of a Tick is an independent instance whose identity is not a Pane ID. Tickhost runs every local Tick (extension, Terminal and Shell Ticks), as `hosted:` and `shell:` instances; Artifact Ticks live in the Artifacts service. A program a person starts in a Pane or terminal is not a Tick.
- **Loop**: each Chat has one Loop, which holds the execution state; a Goal is an optional completion condition. Tick Subscriptions belong to the Loop; opening, discovering or reading a Tick never subscribes.
- **Extension Ticks** speak Tick protocol 3: line-delimited JSON-RPC over stdin/stdout, `tick/describe`, `tick/read`, `tick/call` and `tick/update` notifications, state is only `{seq, data, at?}`, and approval binds to the `revision` the Tick reports. TickManage `open` resolves a bare `tick-<name>` against the Tick program of the installed, enabled plugin `<name>` in the configuration root, then PATH: a disabled plugin is refused, by name or by the path to its program; a damaged plugin store refuses instead of falling back to PATH; a plugin without a Tick program falls through to PATH. A plugin program whose manifest declares the protocol always uses it; any other program uses it when opened with `protocol: true`, and otherwise runs in a PTY as a Terminal Tick. A descriptor may declare `screen.min_rows` (an integer 6–14, default 6) and `screen.max_rows` (an integer no less than `min_rows`); an invalid value fails initialization. A Tick must be usable at 30 columns, redraw its whole screen after SIGWINCH and never require a double Esc. Any Tick may declare key bubbling in its terminal output (`ESC ] 7777 ; tickloop ; bubble=on|off` and `key=<name>` for `esc`, `up`, `down`, `left`, `right`, `tab`, `backtab`, ended by BEL or ST; see the specification); Tickhost removes these sequences from the screen, keeps whether each Tick bubbles keys and sends each bubbled key to the view that typed last, else the newest. A Tick that sets DEC mode 1004 gets `ESC [ I` while any card or full-screen view of it has the keyboard and `ESC [ O` otherwise (once when it asks, then on each change); a Tick that has not set it never gets either.
- **Views**: Extension Ticks are shown as cards in the agent Console's Monitor column, inside Herdr or not (ADR 0040); Terminal Ticks and Shells have no card and show full screen in the current terminal (ADR 0044). There is no popup or Herdr view Pane, TickManage has no `placement` or `move`, and there is no ReadWorkspace. A card or a full-screen view is a view attached to Tickhost; hiding or leaving it neither ends the Tick nor changes its identity; end a Tick with TickManage `close` or from the Monitor. A full-screen view takes the whole terminal, from `Enter` or a double click on a Terminal Tick's or a Shell's row, or from `tickloop attach [<instance>]` in any terminal, which lists the local Ticks and Shells of every running Chat of the configuration root and asks for the same one-time view grant through the Chat that owns the instance; its Tick's terminal takes the whole terminal's size but its last row, which the view keeps for its keys, with several views the one typed into last, else the newest. `screen.min_rows` and `screen.max_rows` apply only to cards. A card sits under the Tick's Monitor row: a rule, then the Tick's screen of exactly its `screen.min_rows` rows, as wide as the Monitor column minus its separator (default 40, at least 30 columns). Height the list leaves over goes to cards that declare `screen.max_rows`, shared fairly up to each maximum, and the rest stays empty below the list; when cards do not fit, the focused one stays first, then the selected row's (a Tab preview, or an open card revealed while selected; see Interaction rules), then the ones the user opened (most recent first), then the ones the Agent showed; the others collapse, staying open with nothing on the screen to say so, and show again once there is room. When the Agent uses a Tick or a turn takes in its update, its card shows without moving the focus or selection, unless the user hid it since last showing it; the list then scrolls it into view only while the user is outside the Monitor. Switching the Console to another Chat, a Subagent's included, closes the shown Chat's cards and detaches their views; for the Console's lifetime each Chat remembers its shown cards with who showed them (not a Tab preview) and the ones the user hid, and returning re-shows those whose Tick is still listed with a live screen, each attaching with a fresh grant; no card takes the keys back, and a Chat left from a focused card returns with the keys in the input. The list groups rows as Artifacts, Ticks (extension Ticks), Terminals (Terminal Ticks) and Shells; within a group the row that joined the Monitor last comes first (an Artifact by when it was linked, a hosted Tick or Shell by its time-ordered identity, a reopened Tick in the place of the row it took over); updates never move or scroll a row, and a selected row that leaves hands the selection to the row taking its place (the previous one when it was last). The Tick's terminal follows its card's size (with several cards, the one typed into last, else the newest), at most one resize per 100 ms while the size keeps changing, the final size always and at once when a separator drag ends; it starts at 120x30 until a card attaches and keeps its last size after the last one detaches. Herdr Panes host only Agent Views; the Herdr integration follows the installed version's CLI/schema and never upgrades or restarts the user's Herdr.
- **Subscriptions** have exactly four frequencies: immediate (fixed for Shell), high every minute (the default for extension and Terminal Ticks), medium every 10 minutes and low every 30 minutes. State updates deliver only the latest: an extension Tick's business change, a Terminal Tick's screen text that differs from the last delivery when due, a Shell's exit. Content present at subscribe time only sets the baseline; later joins and resubscriptions after a restart each get their own starting point. A restart or reopen requires choosing again; old subscriptions are never silently rebound. Which changes wake the Agent follows one rule: a change the Agent asked to watch (a Tick Subscription, at its frequency, a Terminal Tick's exit at once; its own Shell's exit) is a Trigger that starts a turn when idle or joins the running one; any other change to a hosted Tick the Chat opened, outside the model's own calls (the user reopening or closing it from the Monitor, its program exiting without a subscription, its host lost), never wakes it and reaches the model once, in a host note at the end of its next request, which in a running turn is its next model call. New Tick state changes follow the same rule. Quiet periods without model calls, merging while busy and stop rules belong to the existing Loop runtime.
- **Artifacts** do not accept Tick Subscriptions; an Artifact Association delivers each @tickloop feedback to every linked agent of the same user, and feedback has no task-execution state.
- **Lifecycle**: detach/attach keeps processes alive. Closing an Agent Pane, `/exit` or View EOF only leaves the interface; the agent keeps running in the local daemon. Shells end when their ordinary Worker exits; a planned upgrade hands ownership over first. Nothing resumes on its own after a process restart: loading history restores only conversation and task facts, and the user continues explicitly. The Agents overview keeps ended root Agents listed from a registry in the configuration root, and only the user continues them. Continue only restores Trigger receiving; a paused Goal also needs `/goal resume`.
- **Tool execution**: resolve the target and arguments first, then carry the same single prepared result through approval and execution. A timeout or cancellation after dispatch yields OutcomeUnknown, and mutating operations are never re-sent automatically. Skills grant no extra permissions.
- **Instruction Files**: a Chat reads them at its first request and again after compaction or a reload; a Subagent takes its parent's. The user's own come from `AGENTS.md` in the configuration root, or `~/.claude/CLAUDE.md` and `~/.claude/rules` without it; then every directory from the filesystem root down to the Folder contributes its `AGENTS.md`, or without one its `CLAUDE.md`, `.claude/CLAUDE.md` and unconditional `.claude/rules`, followed by its `CLAUDE.local.md`. `@path` imports follow their file; a project file imports nothing outside the Folder. Together with the date in the user's time zone they form the user context message, which leads every conversation request and grants no permissions; when the date moves on, a host note at the end of the conversation tells the new one and the cached message stays. Only the Daemon passes the home directory, so tests never read the developer's own files.
- **Subagents**: `Subagent` delegates for real and, as in Claude Code, runs in the background: the call returns at once and the child's completion arrives as a task notification. A family follows its root's host: the terminal (Daemon and Console) always backgrounds and does not offer `run_in_background`; a non-interactive host (`ToolPolicy::durable_chat` and other Harness hosts that choose `SubagentLaunch::BackgroundByDefault`) backgrounds by default and lets the model pass `run_in_background: false` to wait for the final report. Messages enter the receiving Loop automatically, an idle receiver starts a new turn, and the model never polls an inbox. Subagents may delegate further, up to three levels; all descendants belong to one family, and follow-up input keeps the original authorization ceiling. The root can stop any descendant subtree, a member only its direct children's subtrees; `/stop` on an agent also stops all its descendants. One-to-one messages within a family and shared Tasks are available; the Task tools are controlled by a single Settings switch, off by default. Cross-family communication, broadcast and automatic task claiming are not provided yet. Native ACP is an AgentAccess client; see Managed clients.

- **Hooks**: user settings, enabled plugins and the Folder's `.claude/settings.json` and `.claude/settings.local.json` supply Claude Code-format `command` hooks; repository files contribute only `hooks`. Code Settings discovers sources and trust, Harness runs the engine, and Execution Environment executes one-shot commands outside the sandbox, without Tickhost or Shell records. User hooks need no confirmation; plugin and repository hooks require the user's content-bound trust. Unconfirmed, modified or unreadable fingerprints never run, including in Subagents and managed clients. Only user hooks can allow, after deterministic permission checks; plugin and repository hooks may deny, ask, rewrite input and add context. A final input rewrite by either drops a user hook's allow. Hook trust is separate from plugin enablement, and the model cannot grant it.
- **Plugin Commands**: enabled-plugin Markdown Commands register as Skills named `<plugin>:<command>`; nested directories add colon segments, and Commands win a full-name collision with ordinary plugin Skills. Invocation may preprocess Shell blocks through normal Bash preparation, approval and execution; discovery and completion never execute them. `allowed-tools` and `model` warn and are ignored; `@file` remains text with guidance to use Read. These components grant no extra permissions.

- **Managed clients**: ACP and Print create isolated managed Workers with expiring control leases. Settlement ends invocation-owned Shells and hosted Ticks; release retires the Worker. Loading an ACP session restores history only and never starts model, tool or MCP work. Client-supplied resource URIs grant no file or network permission. Settlement also cancels and drains that Chat's background hooks, including runtime async handoffs, within 10 seconds; timeout or unknown command outcome fails settlement without resending. Managed profiles disable independent Triggers, questions, Plan approvals and delegation; ordinary Console lifecycle is unchanged.

## Permissions and tools

- The AI acts only within existing authorization: read and write authorization are judged separately, and a new integration never widens existing permissions. Repository content cannot add permissions; persistent rules come only from the user's own `settings.json` (partitioned by working directory).
- Bash Deny and Ask rules inspect compound commands, assignments, wrappers (including `env` and `sudo`), program paths and potentially matching command substitutions before Auto fast paths or review. Allow keeps its conservative matching. A hook's `if` uses the same restriction matcher, but runs when matching is indeterminate; see "Bash Deny and Ask rules" and "PreToolUse hooks" in `harness/policy/src/auto_policy/README.md`.
- Auto mode deliberately counts the other verified linked worktrees of the Folder's Git repository as the workspace for its Accept Edits fast path, as Claude Code does; this is intended, not a widening to undo. Accept Edits and Plan modes, sensitive paths and Ask/Deny rules are unchanged; see "Linked worktrees" in `harness/policy/src/auto_policy/README.md`.
- When adding or changing a model tool, decide its Auto-mode handling at the same time: mark read-only tools `HostToolPermission::ReadOnly`; for tools with side effects, map them against the frozen default policy in `harness/policy/src/auto_policy/` (`defaults.json`, plus the README's mapping, "not applicable" list and counts), and add tests so ordinary user requests are not wrongly denied in Auto mode while overreaching operations are still blocked. Read that directory's README first.
- The names, parameters, behavior and result text of the general tools (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`, `TaskStop`, `WebFetch`, `WebSearch`, `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `Skill`) are a stable contract; parameters this project adds must be optional.
- Every tool input schema is a flat object: top-level `type: object` with `properties`. A tool with several forms distinguishes them with an enum field and checks the per-form rules at runtime. Do not use `oneOf`/`anyOf`/`allOf`: GLM and other OpenAI-compatible models emit empty arguments for them.
- A new model protocol is only a new adapter in `harness/model`; the runtime and tool execution contain no vendor checks. The provider catalog is compiled into the program (`harness/model/src/providers/*.yaml`, registered in `harness/model/src/cards.rs`); read the project Skill `.tickloop/skills/model-integration/` before changing models or provider integrations.
- A subagent's Bash and direct `!` Shell run under the frozen parent permissions, current tightening rules and single-use approval; the cwd is not an OS sandbox. A family shares its own private temporary-result/scratchpad directory; other families get no access, and symlinks escaping it are not allowed either.
- Native Tick guidance belongs in the fixed tool descriptions, not a prerequisite Skill. Each data source's argv belongs in its Tick package's `<package>:usage` Skill. Keep tool descriptions independent of live instances and login state; retire loaded guidance with an appended host note, never by rewriting conversation history.

## Interaction rules

Lists and menus navigate with `Ctrl+N`/`Ctrl+P` and the arrow keys; text input uses the plain editing mode (ADR 0010). Follow these rules when adding or changing input, completion, pickers, permission menus and task views:

- Text input (including Shell input) has only the plain editing mode, no Vim mode; `Ctrl+G` edits the current input in an external editor at any time.
- Every list, menu, picker, panel and pager that moves with the arrow keys also moves with `Ctrl+N` (down/next) and `Ctrl+P` (up/previous); they confirm with `Enter` and go back or cancel the current screen with `Esc`. `j`/`k` keep working wherever they did, but key hints, `?` help and user documentation show `Ctrl+N`/`Ctrl+P` or the arrows, never `j`/`k`. In text input `j`/`k` stay text, and completion candidates use `Ctrl+N`/`Ctrl+P`.
- Menu and picker options show no numbers and have no hidden number shortcuts. Lists that share `list_row` (the Monitor, the Subagents panel and others) mark the current item only with the selection background, without a leading marker; menus, pickers, permission and question pages mark it with the `❯` cursor (optionally with the selection background too).
- `Esc` works layer by layer (a focused Tick card handles it as described below): first it closes candidates or the current overlay; closing a view and stopping work are separate actions. On the agent's main input with no candidates or overlay to consume it: when the conversation is scrolled up, it returns to the latest; while running, or when idle with an active Goal or self-paced `/loop` and an empty input, `Esc` interrupts the current turn (if any), pauses the active Goal and ends the self-paced `/loop` (deleting its task), while other Triggers keep arriving; in other idle cases, pressing `Esc` twice within 800 ms clears the draft, or opens Rewind on an empty input.
- `Ctrl+C` in the agent input: overlays and candidates get it first; with text in the input it clears it; while running with an empty input it equals `Esc`; when idle with an empty input it leaves the interface (in the Agents overview it needs two presses within 800 ms), and the agent keeps running in the daemon. `/stop` stops the whole Loop; see "Stop" in CONTEXT.md.
- In the Monitor list, `Space` shows or hides the selected Tick's card and keeps focus on the list; `Enter` enters the Tick, expanding its card first if needed; leaving keeps the card open, and several cards can be open. On the row of an ended Tick this Chat opened (hinted `space reopen`), `Space` reopens it and shows the new instance's card as the user's with the focus left on the list, and `Enter` reopens it and enters that card; an ended Tick another Chat opened reopens with neither. `z` hides every shown card (user-opened, Agent-shown and a Tab preview alike) without counting as the user hiding them, so the Agent's use shows them again; `Z` (Shift+z) shows the card of every row that can have one as the user's, as `Space` on each, a Tab preview included, the higher rows taking the room first; both keep the focus and selection on the list. Clicking an extension Tick's row equals `Space`, clicking an open unfocused card equals `Enter`, and a drag or text selection toggles nothing. A row keeps its own state glyph whether its card shows or not; a card collapsed for lack of room adds nothing to its row or the list, and `Space` or a click on that row while it is still collapsed shows it as the user's most recent instead of hiding it. This applies to extension Ticks. Terminal Tick and Shell rows have no card: `Space`, a Tab preview, `z`/`Z` and the Agent's use show nothing for them, and `Space` on an ended Terminal Tick says what `Enter` does; `Enter` or a double click shows them full screen (a single click only selects): a Terminal Tick whose program exited shows its last screen, and a gone one this Chat opened reopens in place first.
- In the Monitor list `↓`/`↑` and `ctrl+n`/`ctrl+p` move the selection one row, stopping at either end, and `Tab`/`Shift+Tab` select the next/previous row of any kind in list order, wrapping. Only `Tab`/`Shift+Tab` (and `tab`/`backtab` a card bubbled) open a card: a row with a live screen whose card is not open shows it at once as a preview, which closes when the selection moves on by any means or the list loses the keyboard, is never remembered per Chat, and stays as the user's only through `Enter`, a click inside it, entering it or `Z`; `Space` hides it like any shown card, and `z` closes it. Every other move (the keys above, an edge line, a bubbled `up`/`down`, the list taking the keyboard, or a removed row handing the selection on) only selects the row. Whichever way the selection lands, while the list has the keyboard the selected row's card, if open (a preview, the user's or the Agent's), shows at once right after the focused card, ahead of the user's, so one collapsed for lack of room shows; who showed it stays the same, and when the selection moves on or the list loses the keyboard it goes back to its own place and the cards it squeezed out come back. Tab in the input box keeps its own meaning. Rows with unseen updates above or below the visible part of the list are counted on an edge line (`↑ 2 updated`, `↓ 1 updated`); a click on an edge line selects one; `n` is not a list key and, like any character the selected row does not bind, leaves the list and is typed into the input. The selected row's status line shows only while the list has the keyboard; an action's error still shows. No user action in the Monitor (showing, previewing, revealing or entering a card, opening a row or its detail, closing a detail, clicking an edge line) marks a row read: read state belongs to the Agent, which handles an update by taking it in or reading the instance.
- A focused Tick card passes input bytes to the Tick unchanged, `Ctrl+C` and every other Ctrl key included; there is no prefix key. A lone `Esc` reaches the Tick at once; a second lone `Esc` within 300 ms, with no other key between, leaves the card and never reaches the Tick. When the Tick bubbles a key: `esc` leaves at once, `up`/`down` return to the list with the previous/next shown card's row selected (the card's own row past either end), `left` goes to the input (closing an overlay Monitor), `right` does nothing, and `tab`/`backtab` return to the list and act as Tab/Shift+Tab there, selecting the next/previous row and previewing its card; none of them enters another card, which takes Enter or a click, and the card left stays shown. Once the focus is on the list or the input, keys are handled there. `h`/`j`/`k`/`l` never bubble. Clicking outside the card leaves it and then acts as a click there (another row's card toggles, another open card is entered); clicks inside reach the Tick only if it enabled mouse reporting. The key-hint line shows `esc esc back to list`, or `esc or esc esc back · ↑↓ tab move` for a Tick that bubbles keys. A card whose Tick ended loses the focus, keeps its last screen and says how on its rule (`exited N`, `ended`, `lost`). Inside a Tick program, the back key is `Backspace` instead of `Esc`; a Tick should not use `Esc` and never requires a double Esc; text input there is plain editing too, and `Ctrl+C` cancels an edit.
- A full-screen view keeps the terminal's last row for its keys (`esc esc hide` for a running Tick), underlined where a click acts as they say (hiding, reopening; never stopping), and passes input bytes to its Tick unchanged, Ctrl keys included. While the Tick does not ask for mouse reports (and always on a Shell's screen or an ended Tick's), the view takes the mouse: the wheel moves as the arrow keys, and a drag selects text in inverse and copies it when let go, as the Console copies (the local pasteboard, a tmux buffer, OSC 52), the hint row saying `Copied`; a Tick that asks for mouse reports gets them, and the terminal's own modifier such as Shift still selects natively. A lone `Esc` reaches the Tick at once and shows `Press esc again to hide` on that row, and a second lone `Esc` within 1 second, with no other key between, hides the view and never reaches the Tick; a bubbled `esc` hides it at once and other bubbled keys do nothing. A Shell's full-screen view is read-only and lists its keys on its last row: a lone `Esc` hides it, `↑`/`↓`, `Ctrl+P`/`Ctrl+N`, `PageUp`/`PageDown` and `Home` scroll back through its output (each view on its own), `G`, `End` or scrolling to the bottom follow the newest output again, and `Ctrl+C` stops a running Shell in the Console but not in `tickloop attach`. While a view is shown, permission requests and questions wait, the terminal rings once, and they show once it is hidden; a Terminal Tick whose program exited keeps its last screen, its bottom row saying how and what is left (`exited 0 · enter reopen · esc hide`): a lone `Esc` hides it and, in the Console for a Tick this Chat opened, `Enter` reopens it in its row's place and shows the new instance full screen; a Shell that ended stays shown with its final output and is never reopened. Hiding returns to the Monitor list with the row still selected, or ends `tickloop attach`, whose picker follows the list rules above.
- Destructive row actions on the Monitor and similar lists (removing or closing a Tick, stopping a Shell, unlinking an Artifact, deleting a scheduled task, uninstalling a plugin, removing a marketplace, disabling or restoring a Hook in `/hooks`, stopping an Agent or removing an ended Agent's row in the Agents overview) all take two presses of plain `x` within 3 seconds, with no confirmation dialog: the first press shows a red `Press x again to …` on the key-hint line, and only a second press on the same row within 3 seconds acts. Expiry, moving the selection, any other key or leaving cancels it.
- Keys act only on the visible, focused screen; permission, question and workflow menus handle keys separately from the input editor, and hidden screens consume no input. On-screen hints must match the actual key behavior.

| `vendor/crossterm/` | crossterm copy patched in through Cargo; read `vendor/crossterm/UPSTREAM.md` before changing it |

Dependency boundaries:

- Code crates (`tickloop-code-*`, with entry package `tickloop-code` and binary `tickloop`) use Harness only through `tickloop-harness` in `harness/sdk`. Harness implementation crates use the `tickloop-harness-*` prefix.
- Facade consumers select the capabilities they use: `protocol` and `ids` are always exported; `base` is optional and enabled by `tools`, `model`, `artifacts`, `connector`, `policy`, `engine` and `test-support`. Keep `cron`/`transcript` consumers free of base and its image/network dependencies.
- Harness depends on its own crates, `tick/ids`, `tick/protocol`, `tick/oauth` and third-party libraries; `tick/oauth-test-server` is allowed only as a dev-dependency. OAuth has only third-party production dependencies; package credential storage and its OAuth adapter belong to `tick/packages`; `harness/connector` depends on `harness/base` and `tick/oauth`, and Code supplies its credential files. Tests composing Code Settings or Local Environment live in Code. `scripts/dependency-boundaries.json` enforces these boundaries without exceptions, including dev and build dependencies; Harness never depends on Code or Tickhost.
- `tick/`, `tickhost/` and `ui/` depend on no Harness or Code crate. Tick authors use the Tick public layer and `ui`; writing a Tick never requires Harness or Code, whose crates are internal implementation and are not a stable Tick-author API. `tick/plugins` depends only on `tick/packages` and third-party libraries.
- `code/console` reaches Agents through AgentAccess (`code/client` and `code/access`); the facade's engine/test-support features, Daemon, Local Environment and `tickhost/host` are dev-dependencies only. Its production facade features expose model, tools, artifacts and connector without the runtime.
- `harness/protocol` depends only on `tick/protocol`, `tick/ids` and basic libraries such as serde; `harness/transcript` only on `harness/protocol`, `tick/ids` and basic libraries.
- `tick/ids` depends only on `uuid` and `serde`; every Tickloop ID is generated through it.

Integration seams: Transcript Store, Execution Environment, Model Endpoint, Credential Source and Settings Store. Harness owns generic Tick tools, approval, subscriptions, Trigger delivery, Shell tasks and the Hook engine. Execution Environment binds authorization to a Port with inspect/prepare/execute/observe; Code's Local Environment implements it with Tickhost, and Daemon injects it. Settings Store keeps permission and Hook trust writes in Harness while Code persists settings.json and discovers Hook sources. File tools, file history, Rewind and `@` mentions reach the Folder and Additional Directories through the Chat's Port, which reports each directory's root name and file capability; the Harness maps paths to roots and the environment enforces them, while the Harness's own Chat directories and file-history backups stay on this machine (ADR 0042). A Folder whose root the Port reports without a local path is only in the environment: the Harness neither resolves nor trusts it here, shows Bash and TaskStop only when the Port runs Shells and never falls back to a local shell, and gives it no scratchpad, plan file, project settings, instruction files, project Skills or hooks, and the Folder-less WebFetch reach. Nor does the Harness keep records for such a Chat on this machine: there is no Chat directory, so large tool results are cut with a note to the model instead of stored, changes get no review artifact, and no Artifact feedback inbox, Trigger lease or Tick watermark is kept; there are no file-history backups, so Rewind reports each file it edited as not restored. The known gap: when the Port runs Shells, their output is still written to the Chat's task directory on this machine. Without a Chat directory such a Chat takes no Trigger lease, so its host must keep waits durably (`WaitHosting::Durable`) and deliver Artifact feedback with `TurnOp::Deliver`; under process-held waits with a Transcript, its Triggers are refused as no longer loaded and event-source feedback is not delivered. In any Chat, a file in a root the Port reports without a local path likewise gets no backup or review artifact; an Agent with an environment also has Chats without a Folder, which can gain and lose one (`set_working_directories`). File tools do not run in the sandbox. The runtime registers Tick adapters only for `hosted` and `shell`; Artifacts reach the Loop through Artifact Association. Tickhost executes Shell requests bound to a single-use spawn authorization. The Loop holds no Herdr layout state, and data sources stay in Tick packages. Generic TickCall reads the catalog and then calls; no model tool is generated per instance.

## Verification and tickets

- Check commands and where and how to write tests follow only "Checks" and "Writing tests" in CONTRIBUTING.md; a change is done when `make check-workspace` passes.
- When reporting verification, list the evidence separately for local automated checks, the real host (Tickhost, plus Herdr when Agent Panes are involved), real models and user actions; a design record is not runtime acceptance.
- Logs, results, evidence, transcripts and caches produced by scripts go where `.gitignore` excludes them; CRLF from PTY and other run output never goes into source files.
- Public collaboration uses GitHub Issues and Pull Requests. Maintainer-local tickets follow `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`: read the whole ticket, its parent spec and dependency status before implementing; Status is triage state, Progress is implementation progress, and done requires acceptance evidence.
