# Tickloop

Tickloop (tickloop.ai) is a terminal AI agent for code and office work: the `tickloop` command starts the agent, and Tickhost runs every local Tick. This repository is a domain-agnostic host: it knows no Tick kinds, domain concepts or specific package programs. Official Tick packages (programs, manifests and Skills) and their releases live in [tickloopai/ticks](https://github.com/tickloopai/ticks); this repository keeps only the plugin mechanism. Accepting a host integration never requires a real data-source account.

## Baseline and documents

- Terms follow [CONTEXT.md](./CONTEXT.md); use its names in code, UI and discussion. Internal module boundaries are not product Tick types.
- When a change conflicts with documented behavior, say so; never change a meaning silently. When documents and source disagree, the source wins.
- Division of documents: agent instructions live only in AGENTS.md (no CLAUDE.md); CONTEXT.md holds term definitions only; the READMEs describe user-facing usage only.
- `docs/` (design records `docs/design/`, ADRs `docs/adr/`, `docs/agents/`), `code/cli/README.md` (the agent manual, in Chinese), `.tickloop/skills/` and `.scratch/` are maintainer-local files outside Git. Pointers to them below apply only when they exist; in a contributor's checkout, this file, CONTEXT.md, the READMEs and the source are authoritative. When reading an ADR, check its frontmatter `status` and follow "superseded by" to the ADR that replaces it.

## Core behavior

- **Tick Instance**: each run of a Tick is an independent instance whose identity is not a Pane ID. Tickhost runs every local Tick (extension, Terminal and Shell Ticks), as `hosted:` and `shell:` instances; Artifact Ticks live in the Artifacts service. A program a person starts in a Pane or terminal is not a Tick.
- **Loop**: each Chat has one Loop, which holds the execution state; a Goal is an optional completion condition. Tick Subscriptions belong to the Loop; opening, discovering or reading a Tick never subscribes.
- **Extension Ticks** speak Tick protocol 3: line-delimited JSON-RPC over stdin/stdout, `tick/describe`, `tick/read`, `tick/call` and `tick/update` notifications, state is only `{seq, data, at?}`, and approval binds to the `revision` the Tick reports. TickManage `open` resolves a bare `tick-<name>` against the Tick program of the installed, enabled plugin `<name>` in the configuration root, then PATH: a disabled plugin is refused, by name or by the path to its program; a damaged plugin store refuses instead of falling back to PATH; a plugin without a Tick program falls through to PATH. A plugin program whose manifest declares the protocol always uses it; any other program uses it when opened with `protocol: true`, and otherwise runs in a PTY as a Terminal Tick. A descriptor may declare `screen.min_rows` (an integer 6–14, default 6) and `screen.max_rows` (an integer no less than `min_rows`); an invalid value fails initialization. A Tick must be usable at 30 columns, redraw its whole screen after SIGWINCH and never require a double Esc. Any Tick may declare key bubbling in its terminal output (`ESC ] 7777 ; tickloop ; bubble=on|off` and `key=<name>` for `esc`, `up`, `down`, `left`, `right`, `tab`, `backtab`, ended by BEL or ST; see the specification); Tickhost removes these sequences from the screen, keeps whether each Tick bubbles keys and sends each bubbled key to the view that typed last, else the newest. A Tick that sets DEC mode 1004 gets `ESC [ I` while any card of it has the keyboard and `ESC [ O` otherwise (once when it asks, then on each change); a Tick that has not set it never gets either.
- **Views**: Ticks are shown only as cards in the agent Console's Monitor column, inside Herdr or not (ADR 0040). There is no popup, full-screen view or Herdr view Pane, TickManage has no `placement` or `move`, and there is no ReadWorkspace. A card is a view attached to Tickhost; hiding or leaving it neither ends the Tick nor changes its identity; end a Tick with TickManage `close` or from the Monitor. A card sits under the Tick's Monitor row: a rule, then the Tick's screen of exactly its `screen.min_rows` rows, as wide as the Monitor column minus its separator (default 40, at least 30 columns). Height the list leaves over goes to cards that declare `screen.max_rows`, shared fairly up to each maximum, and the rest stays empty below the list; when cards do not fit, the focused one stays first, then the ones the user opened (most recent first), then the ones the Agent or Tab showed, and the others collapse. When the Agent uses a Tick or a turn takes in its update, its card shows without moving the focus or selection, unless the user hid it since last showing it; the list then scrolls it into view only while the user is outside the Monitor. Rows keep the order they joined the Monitor (an Artifact by when it was linked, a hosted Tick or Shell by its time-ordered identity); updates never move or scroll a row. The Tick's terminal follows its card's size (with several cards, the one typed into last, else the newest), at most one resize per 100 ms while the size keeps changing, the final size always and at once when a separator drag ends; it starts at 120x30 until a card attaches and keeps its last size after the last one detaches. Herdr Panes host only Agent Views; the Herdr integration follows the installed version's CLI/schema and never upgrades or restarts the user's Herdr.
- **Subscriptions** have exactly four frequencies: immediate (fixed for Shell), high every minute (the default for extension and Terminal Ticks), medium every 10 minutes and low every 30 minutes. State updates deliver only the latest: an extension Tick's business change, a Terminal Tick's screen text that differs from the last delivery when due, a Shell's exit. Content present at subscribe time only sets the baseline; later joins and resubscriptions after a restart each get their own starting point. A restart or reopen requires choosing again; old subscriptions are never silently rebound. Quiet periods without model calls, merging while busy and stop rules belong to the existing Loop runtime.
- **Artifacts** do not accept Tick Subscriptions; an Artifact Association delivers each @tickloop feedback to every linked agent of the same user, and feedback has no task-execution state.
- **Lifecycle**: detach/attach keeps processes alive. Closing an Agent Pane, `/exit` or View EOF only leaves the interface; the agent keeps running in the local daemon. Shells end when their ordinary Worker exits; a planned upgrade hands ownership over first. Nothing resumes on its own after a process restart: loading history restores only conversation and task facts, and the user continues explicitly. Continue only restores Trigger receiving; a paused Goal also needs `/goal resume`.
- **Tool execution**: resolve the target and arguments first, then carry the same single prepared result through approval and execution. A timeout or cancellation after dispatch yields OutcomeUnknown, and mutating operations are never re-sent automatically. Skills grant no extra permissions.
- **Instruction Files**: a Chat reads them at its first request and again after compaction or a reload; a Subagent takes its parent's. The user's own come from `AGENTS.md` in the configuration root, or `~/.claude/CLAUDE.md` and `~/.claude/rules` without it; then every directory from the filesystem root down to the Folder contributes its `AGENTS.md`, or without one its `CLAUDE.md`, `.claude/CLAUDE.md` and unconditional `.claude/rules`, followed by its `CLAUDE.local.md`. `@path` imports follow their file; a project file imports nothing outside the Folder. Together with the date in the user's time zone they form the user context message, which leads every conversation request and grants no permissions; when the date moves on, a host note at the end of the conversation tells the new one and the cached message stays. Only the Daemon passes the home directory, so tests never read the developer's own files.
- **Subagents**: `Subagent` delegates for real and, as in Claude Code, runs in the background: the call returns at once and the child's completion arrives as a task notification. A family follows its root's host: the terminal (Daemon and Console) always backgrounds and does not offer `run_in_background`; a non-interactive host (`ToolPolicy::durable_chat` and other Harness hosts that choose `SubagentLaunch::BackgroundByDefault`) backgrounds by default and lets the model pass `run_in_background: false` to wait for the final report. Messages enter the receiving Loop automatically, an idle receiver starts a new turn, and the model never polls an inbox. Subagents may delegate further, up to three levels; all descendants belong to one family, and follow-up input keeps the original authorization ceiling. The root can stop any descendant subtree, a member only its direct children's subtrees; `/stop` on an agent also stops all its descendants. One-to-one messages within a family and shared Tasks are available; the Task tools are controlled by a single Settings switch, off by default. Cross-family communication, broadcast, automatic task claiming, ACP and Hooks are not provided yet.

## Permissions and tools

- The AI acts only within existing authorization: read and write authorization are judged separately, and a new integration never widens existing permissions. Repository content cannot add permissions; persistent rules come only from the user's own `settings.json` (partitioned by working directory).
- Auto mode deliberately counts the other verified linked worktrees of the Folder's Git repository as the workspace for its Accept Edits fast path, as Claude Code does; this is intended, not a widening to undo. Accept Edits and Plan modes, sensitive paths and Ask/Deny rules are unchanged; see "Linked worktrees" in `harness/policy/src/auto_policy/README.md`.
- When adding or changing a model tool, decide its Auto-mode handling at the same time: mark read-only tools `HostToolPermission::ReadOnly`; for tools with side effects, map them against the frozen default policy in `harness/policy/src/auto_policy/` (`defaults.json`, plus the README's mapping, "not applicable" list and counts), and add tests so ordinary user requests are not wrongly denied in Auto mode while overreaching operations are still blocked. Read that directory's README first.
- The names, parameters, behavior and result text of the general tools (`Read`, `Write`, `Edit`, `Glob`, `Grep`, `Bash`, `TaskStop`, `WebFetch`, `WebSearch`, `AskUserQuestion`, `EnterPlanMode`, `ExitPlanMode`, `Skill`) are a stable contract; parameters this project adds must be optional.
- Every tool input schema is a flat object: top-level `type: object` with `properties`. A tool with several forms distinguishes them with an enum field and checks the per-form rules at runtime. Do not use `oneOf`/`anyOf`/`allOf`: GLM and other OpenAI-compatible models emit empty arguments for them.
- A new model protocol is only a new adapter in `harness/model`; the runtime and tool execution contain no vendor checks. The provider catalog is compiled into the program (`harness/model/src/providers/*.yaml`, registered in `harness/model/src/cards.rs`); read the project Skill `.tickloop/skills/model-integration/` before changing models or provider integrations.
- A subagent's Bash and direct `!` Shell run under the frozen parent permissions, current tightening rules and single-use approval; the cwd is not an OS sandbox. A family shares its own private temporary-result/scratchpad directory; other families get no access, and symlinks escaping it are not allowed either.
- The system Skill `tickloop` (`harness/policy/skills/tickloop/SKILL.md`) must match the actual tools and permissions and describe only capabilities that exist. Each data source's argv belongs in the Skill shipped with its Tick package (`<package>:usage`), never hard-coded in the system Skill.

## Interaction rules

Lists and menus follow Vim navigation habits; text input uses the plain editing mode (ADR 0010). Follow these rules when adding or changing input, completion, pickers, permission menus and task views:

- Text input (including Shell input) has only the plain editing mode, no Vim mode; `Ctrl+G` edits the current input in an external editor at any time.
- Lists and menus navigate with `j`/`k` and `Ctrl+N`/`Ctrl+P`, confirm with `Enter`, and go back or cancel the current screen with `Esc`. In text input `j`/`k` stay text, and completion candidates use `Ctrl+N`/`Ctrl+P`.
- Menu and picker options show no numbers and have no hidden number shortcuts. Lists that share `list_row` (the Monitor, the Subagents panel and others) mark the current item only with the selection background, without a leading marker; menus, pickers, permission and question pages mark it with the `❯` cursor (optionally with the selection background too).
- `Esc` works layer by layer (a focused Tick card handles it as described below): first it closes candidates or the current overlay; closing a view and stopping work are separate actions. On the agent's main input with no candidates or overlay to consume it: when the conversation is scrolled up, it returns to the latest; while running, or when idle with an active Goal or self-paced `/loop` and an empty input, `Esc` interrupts the current turn (if any), pauses the active Goal and ends the self-paced `/loop` (deleting its task), while other Triggers keep arriving; in other idle cases, pressing `Esc` twice within 800 ms clears the draft, or opens Rewind on an empty input.
- `Ctrl+C` in the agent input: overlays and candidates get it first; with text in the input it clears it; while running with an empty input it equals `Esc`; when idle with an empty input it leaves the interface (in the Agents overview it needs two presses within 800 ms), and the agent keeps running in the daemon. `/stop` stops the whole Loop; see "Stop" in CONTEXT.md.
- In the Monitor list, `Space` shows or hides the selected Tick's card and keeps focus on the list; `Enter` enters the Tick, expanding its card first if needed; leaving keeps the card open, and several cards can be open. Clicking a Tick row equals `Space`, clicking an open unfocused card equals `Enter`, and a drag or text selection toggles nothing. A row keeps its own state glyph whether its card shows or not; a card collapsed for lack of room ends its row with `collapsed`. This applies to extension, Terminal and Shell Ticks; Shell cards are read-only.
- `Tab`/`Shift+Tab` in the Monitor list select the next/previous row of any kind in list order, wrapping; a row that can have a card shows it as a preview, which closes when Tab moves on unless `Enter`, a click or entering it keeps it (`Space` shows or hides any card, a preview included); a row without a card is only selected. Tab in the input box keeps its own meaning. Rows with unseen updates above or below the visible part of the list are counted on an edge line (`↑ 2 updated`, `↓ 1 updated`); `n` in the list (hinted `n next update` while such rows exist) or a click on an edge line selects one. The selected row's status line shows only while the list has the keyboard; an action's error still shows. No user action in the Monitor (showing, previewing or entering a card, opening a row or its detail, closing a detail, jumping with `n`) marks a row read: read state belongs to the Agent, which handles an update by taking it in or reading the instance.
- A focused Tick card passes input bytes to the Tick unchanged, `Ctrl+C` and every other Ctrl key included; there is no prefix key. A lone `Esc` reaches the Tick at once; a second lone `Esc` within 300 ms, with no other key between, leaves the card and never reaches the Tick; a Shell's read-only card leaves on a lone `Esc`. When the Tick bubbles a key: `esc` leaves at once, `up`/`down` return to the list with the previous/next shown card's row selected (the card's own row past either end), `left` goes to the input (closing an overlay Monitor), `right` does nothing, and `tab`/`backtab` return to the list and act as Tab/Shift+Tab there, selecting the next/previous row and previewing its card; none of them enters another card, which takes Enter or a click, and the card left stays shown. Once the focus is on the list or the input, keys are handled there. `h`/`j`/`k`/`l` never bubble. Clicking outside the card leaves it and then acts as a click there (another row's card toggles, another open card is entered); clicks inside reach the Tick only if it enabled mouse reporting. The key-hint line shows `esc esc back to list`, `esc or esc esc back · ↑↓ tab move` for a Tick that bubbles keys, or `esc back to list` on a read-only Shell card. A card whose Tick ended loses the focus, keeps its last screen and says how on its rule (`exited N`, `ended`, `lost`). Inside a Tick program, go back a level with `Backspace`; a Tick may use `Esc` but never requires a double Esc; text input there is plain editing too, and `Ctrl+C` cancels an edit.
- Destructive row actions on the Monitor and similar lists (removing or closing a Tick, stopping a Shell, unlinking an Artifact, deleting a scheduled task, uninstalling a plugin, removing a marketplace) all take two presses of plain `x` within 3 seconds, with no confirmation dialog: the first press shows a red `Press x again to …` on the key-hint line, and only a second press on the same row within 3 seconds acts. Expiry, moving the selection, any other key or leaving cancels it.
- Keys act only on the visible, focused screen; permission, question and workflow menus handle keys separately from the input editor, and hidden screens consume no input. On-screen hints must match the actual key behavior.

Dependency boundaries:

- Code crates (`tickloop-code-*`, with entry package `tickloop-code` and binary `tickloop`) use Harness only through `tickloop-harness` in `harness/sdk`. Harness implementation crates use the `tickloop-harness-*` prefix.
- Facade consumers select the capabilities they use: `protocol` and `ids` are always exported; `base` is optional and enabled by `tools`, `model`, `artifacts`, `connector`, `policy`, `engine` and `test-support`. Keep `cron`/`transcript` consumers free of base and its image/network dependencies.
- Harness depends on its own crates, `tick/ids`, `tick/protocol`, `tick/oauth` and third-party libraries; `tick/oauth-test-server` is allowed only as a dev-dependency. OAuth has only third-party production dependencies; package credential storage and its OAuth adapter belong to `tick/packages`; `harness/connector` depends on `harness/base` and `tick/oauth`, and Code supplies its credential files. Tests composing Code Settings or Local Environment live in Code. `scripts/dependency-boundaries.json` enforces these boundaries without exceptions, including dev and build dependencies; Harness never depends on Code or Tickhost.
- `tick/`, `tickhost/` and `ui/` depend on no Harness or Code crate. Tick authors use the Tick public layer and `ui`; writing a Tick never requires Harness or Code, whose crates are internal implementation and are not a stable Tick-author API. `tick/plugins` depends only on `tick/packages` and third-party libraries.
- `code/console` reaches Agents through AgentAccess (`code/client` and `code/access`); the facade's engine/test-support features, Daemon, Local Environment and `tickhost/host` are dev-dependencies only. Its production facade features expose model, tools, artifacts and connector without the runtime.
- `harness/protocol` depends only on `tick/protocol`, `tick/ids` and basic libraries such as serde; `harness/transcript` only on `harness/protocol`, `tick/ids` and basic libraries.
- `tick/ids` depends only on `uuid` and `serde`; every Tickloop ID is generated through it.

Integration seams: Transcript Store, Execution Environment, Model Endpoint, Credential Source and Settings Store. Harness owns generic Tick tools, approval, subscriptions, Trigger delivery and Shell tasks. Execution Environment binds authorization to a Port with inspect/prepare/execute/observe; Code's Local Environment implements it with Tickhost, and Daemon injects it. Settings Store keeps permission writes in Harness while Code persists settings.json. Filesystem tools still access the local Folder directly; sandbox file access is outside this split. The runtime registers Tick adapters only for `hosted` and `shell`; Artifacts reach the Loop through Artifact Association. Tickhost executes Shell requests bound to a single-use spawn authorization. The Loop holds no Herdr layout state, and data sources stay in Tick packages. Generic TickCall reads the catalog and then calls; no model tool is generated per instance.

## Verification and tickets

- Check commands and where and how to write tests follow only "Checks" and "Writing tests" in CONTRIBUTING.md; a change is done when `make check-workspace` passes.
- When reporting verification, list the evidence separately for local automated checks, the real host (Tickhost, plus Herdr when Agent Panes are involved), real models and user actions; a design record is not runtime acceptance.
- Logs, results, evidence, transcripts and caches produced by scripts go where `.gitignore` excludes them; CRLF from PTY and other run output never goes into source files.
- Public collaboration uses GitHub Issues and Pull Requests. Maintainer-local tickets follow `docs/agents/issue-tracker.md` and `docs/agents/triage-labels.md`: read the whole ticket, its parent spec and dependency status before implementing; Status is triage state, Progress is implementation progress, and done requires acceptance evidence.
