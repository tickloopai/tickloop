# Artifact Service account

Tick Loop's Artifact Service account is separate from model Provider sign-in. The user opens `/artifacts` in their own terminal. It starts device authorization when signed out and opens the picker after login; the user opens the displayed service URL in their browser, signs in with Google, and approves the device. `/settings` shows the service account and its Sign out action. These commands work without Herdr.

Read `service_connections.artifacts` in Current host state: `authentication: signed_in` confirms the account, `signed_out` requires `/artifacts` sign-in, and `unknown` means status could not be verified. `tool_directory: unavailable` or missing tools means tool access is unavailable; it does not establish that the user is signed out. Report account state and tool availability separately. Use the installed Artifact MCP tools for all content operations. A delegated child inherits discovered tools within its frozen endpoint/account and permission ceiling; tool restrictions never grant extra access. A Skill grants no permissions.

The current host state includes `artifact_ticks`: artifacts the user added to this Chat. Operate on them through the discovered MCP tools. Adding a Tick grants no permissions and establishes neither a feedback association nor a Tick Subscription.

## Connecting an existing document

When the owner explicitly asks this Agent to receive feedback on an existing artifact, use `mcp__artifacts__artifact_agent_connect` with its `artifact_id` and a new `operation_id`. Connection preserves the body and published versions, including documents that have never been published. Reading a document does not connect it; publishing is reserved for intended content publication.

After `prepared`, call the same tool once with `action: "check"`, the same artifact and operation ID. Report its confirmed status. `associated_current` confirms the association, not that the Agent is online. `already_associated` preserves this Chat's existing Loop and creates no receipt for the new ID. When feedback listening needs recovery, tell the owner to select the artifact in the Tick List and press `f`; reading or reopening history does not resume listening. A stopped or expired Loop remains ended.

For `unknown`, retain the original operation ID and report the uncertainty. Only an explicit owner retry may repeat that exact connection request; a new ID cannot resolve an earlier unknown. `not_current` means the old association has been replaced or cleared. Replacing another association requires explicit owner intent and `replace_existing: true`; a conflict requires reassessment, not automatic takeover. Connect is unavailable during claimed feedback. Continue that request through the edit, reply and completion tools instead.

## Collaborative editing

Markdown must remain editable in the web editor. If a tool returns `unsupported_markdown` or `rewrite_required: true`, the rejected operation did not save the proposed content. Read its reason, rewrite the unsupported formatting while preserving the user's content, and submit the corrected payload with a new operation ID. Keep the last acknowledged draft/stream offset. Never retry the rejected payload unchanged, ignore the error, or report the document complete. Inline code cannot share bold, italic, underline, strike or link formatting; place those styles outside the code span. Unknown outcomes still require operation reconciliation, not rewriting or resending.

For an existing source-only working document, revise its exact targets and publish the corrected working revision. Once that working copy is confirmed clean, read its exact source and current published head. Publish that source with `artifact_publish` and the copied `expected_version_id` to establish an editable working copy. Re-read and confirm `representation: rich` before calling the repair complete. A dirty working copy or changed head requires a fresh read and reassessment; never discard other edits to perform this conversion.

For revisions to an existing artifact, work in its shared document so browser edits and AI changes meet in one working copy:

1. Read `mcp__artifacts__artifact_edit_read`. If no working copy exists and editing is intended, call `mcp__artifacts__artifact_edit_open` with a new operation ID. Opening preserves the published source. Copy `working_id`, `generation`, and the returned target IDs and hashes.
2. Use `mcp__artifacts__artifact_edit_patch` for a bounded replacement, insertion, or deletion. Copy each target's `id` into `target` and `hash` into `expectedHash`; do not calculate these yourself. Paginate `artifact_edit_read` when `next_cursor` is returned. A successful patch saves the shared document and appears for connected collaborators.
3. On `target_conflict` or `working_conflict`, read again and reassess the user's requested change against the new content. Preserve human edits; a fresh read does not authorize replacing them. Several acknowledged patches expose actual progress while you work.
4. When the requested document is complete and publication is intended, the owner calls `mcp__artifacts__artifact_edit_publish`. Copy `durable_revision` to `expected_revision` and `base_version_id` to `expected_version_id`. Return the confirmed published link. An editor can save changes but only the owner publishes. Changes arriving during publication stay in the working copy for a later version.

Use `mcp__artifacts__artifact_operation` after an uncertain dispatched mutation; never automatically resend it or invent a new ID. Whole-document publish, history restore, and draft finish reject a dirty working copy. Continue through the shared-edit tools instead of discarding it. HTML edits remain source until complete publication in the isolated preview.

## Sharing and collaborators

Use `mcp__artifacts__artifact_members` to read access and `mcp__artifacts__artifact_invite` to invite a specific verified Google email with `viewer` or `editor` access. Return the invitation URL for the user to send. Accepting belongs to the matching signed-in recipient through `artifact_invitation_read` and `artifact_invitation_accept`; use their discovered MCP names. The owner manages access with `artifact_member_role`, `artifact_member_revoke`, and `artifact_invitation_revoke`. Member access is separate from the public read-only URL and from owner-only Agent feedback.

When the owner requests removal of all collaborators, read every `artifact_members` page and present the affected members and invitations. Call `mcp__artifacts__artifact_members_clear` with that snapshot's `membership_revision` as `expected_membership_revision`. A changed revision requires a fresh preview and reassessment of the authorized set; do not silently clear people added later. This removes collaborators and disables retained invitation links while preserving the public reading link. For a request to leave someone else's document, use `mcp__artifacts__artifact_member_leave`; it removes only the signed-in user's membership. The user's own minimal leave receipt remains available through `artifact_operation` after access ends. Batch actions have separate per-document outcomes; retain and reconcile each uncertain operation ID.

Public sharing uses `mcp__artifacts__artifact_share_enable` and `mcp__artifacts__artifact_share_revoke`. A new link replaces the old one; its secret URL is returned only once. Check uncertain operation IDs before another change. If the user explicitly chooses to stop sharing despite an unknown earlier sharing change, revoke with that change's `cancel_operation_id`; this also fences a delayed request. Do not cancel an unrelated content operation.

## Finding and renaming

`mcp__artifacts__artifact_list` includes owned and invited documents. Its optional `query` searches titles across the complete authorized directory; ownership, personal group and sort options apply to that directory. Keep all resolved filters and ordering unchanged when following `next_cursor`. A `catalog_conflict` requires starting a fresh list because personal organization changed. For a title change, read `mcp__artifacts__artifact_read`, then call `mcp__artifacts__artifact_rename` with its `metadata_revision` as `expected_metadata_revision`. Owners and editors can rename. The stable link and published source stay the same. On `metadata_conflict`, read the current title and reassess before making another explicit change; reconcile an uncertain result with `artifact_operation`.

## Personal organization and unread updates

Use `mcp__artifacts__artifact_catalog_read` for the signed-in user's groups and preferences. For a requested group creation, rename, reorder, removal, document move or preference change, use `mcp__artifacts__artifact_catalog_change` with that personal `revision` as `expected_revision` and a new operation ID. Groups are personal; deleting one unlinks its documents without deleting their content or changing anyone else's access. On `catalog_conflict`, read the current organization and reassess the intended change. Query `mcp__artifacts__artifact_catalog_operation` for an uncertain request, retaining its exact payload and ID rather than automatically resending.

MCP reads, saves and AI presence do not mean the user has viewed a document. A user's own save does not clear unread changes from other people. Let the visible browser view report its exact content; do not fabricate observation tokens, use a current-head value as proof, or infer human attention from an Agent read. An old-version observation cannot acknowledge later working changes.

## Shared discussion and Agent feedback

Use `mcp__artifacts__artifact_threads` for common discussions visible to current members. Owners and editors can create or reply; viewers can read. To attach a new discussion to a passage, copy `working_id`, `generation`, target `id` and `hash` from `artifact_edit_read` into `artifact_thread_create`'s `working_id`, `generation`, `target_id` and `expected_hash`. Do not encode cursor positions. Reply with `artifact_thread_reply`; resolve or reopen with `artifact_thread_resolve` using the last read thread revision. Query uncertain discussion writes with `artifact_thread_operation`.

`request_ai` and `@AI` record a request. Only an explicit owner instruction authorizes `artifact_thread_forward` for that exact message. The service then delivers the request to the owner's associated Agent; membership does not grant another user's Agent permissions. Existing private comments remain separate from common discussions.

At the start of every claimed feedback attempt, call `mcp__artifacts__artifact_edit_read` for the current working document before deciding what remains. This also applies when only publication, reply or completion remains: the previous attempt or a person may have saved changes since the last run. If no working document exists, inspect the published content with `mcp__artifacts__artifact_read`; use `mcp__artifacts__artifact_edit_open` only when the remaining authorized work requires editing. Preserve the saved work and human edits, then perform only the remaining changes. The claim's optional `prior_progress` identifies confirmed earlier reply/publication operations for this same request. Read their receipts with `artifact_operation` and inspect the current document before deciding what remains. Reuse confirmed prior publication/reply evidence when it still completes the request; an old receipt is not a current claim or permission to replay a mutation. A stream bound to the old claim stays invalidated; its acknowledged content remains in the document.

Use `artifact_feedback_reply` and `artifact_feedback_complete` to report the outcome in the originating thread, supplying the acknowledged operation IDs and published version required by their discovered schemas. An ordinary thread reply or resolving a discussion does not complete a feedback claim. Do not forward or recover another request from a feedback run.

Outside claimed feedback, an explicit owner instruction can recover a `needs-attention` request. Read that exact message and copy its current `feedback.event_id` from `artifact_threads` into `artifact_thread_forward.expected_event_id`; private owner comments use `artifact_comments.feedback_event_id` and `artifact_comment_forward.expected_event_id`. Keep the original message and use one new recovery operation ID. Recovery preserves saved work and queues a new attempt; it neither starts an offline Agent nor resumes a stopped Loop. A stale event/status requires reassessment, not substitution of a newer ID. For an uncertain recovery, retain the exact request and query its operation; repeat it only on an explicit owner retry. A historical committed recovery receipt requires a fresh discussion read before reporting the current request state.

## Shared Markdown generation

Use the installed `artifact_edit_stream_*` tools when generating Markdown into the document that people can edit. For a new artifact, reserve a private empty Markdown document with `mcp__artifacts__artifact_draft_create`, then open its shared working copy. For an existing artifact, read the current working copy first.

1. Call `mcp__artifacts__artifact_edit_stream_begin` with a new operation ID, the read `working_id`/`generation`, and the intended position. For before, after or replace, copy the target ID and hash from the read result. Beginning reserves the position and preserves the current body.
2. Write a useful chunk with `mcp__artifacts__artifact_edit_stream_append`. Copy `stream_id` and the last confirmed `accepted_offset`; supply the chunk as `text` and use a new operation ID. Wait for its committed acknowledgement before writing the next chunk. Offsets are server-provided UTF-8 byte counts. Several separately acknowledged calls show actual saved progress in the shared document.
3. Check `stream_status`, `held_bytes`, `retired_blocks` and warnings after each append. Incomplete syntax may be held. A block edited or deleted by another writer is permanently protected from this stream; preserve that decision. A rejected chunk leaves its input offset unchanged. Reassess unsupported syntax against the requested content rather than forcing a whole-document replacement.
4. Call `mcp__artifacts__artifact_edit_stream_finish` with the confirmed offset when all intended input has been accepted. Finish ends generation; it does not publish. Read the shared document, verify human changes and the generated result, then use the ordinary owner publication step above when publication is intended.

Use `mcp__artifacts__artifact_edit_stream_read` for progress, including an uncertain begin looked up by `begin_operation_id`, and `artifact_operation` for the dispatched mutation's exact receipt. Unknown outcomes do not authorize replay or advancing a guessed offset. If the user explicitly cancels, `artifact_edit_stream_abort` stops a known stream or fences an uncertain begin using `cancel_begin_operation_id`. It preserves already saved content. Expired, restored or otherwise terminal streams require a new intentional stream from a current read; they are not automatically resumed. A historical terminal stream may report `history_available: false`; its old receipt still does not authorize restarting it. Read the current document for its saved content.

## Independent drafts and HTML generation

For HTML generation or an independent draft without collaborative edits, use the installed MCP draft tools and submit actual content chunks as you write them. HTML runs only after complete publication in its isolated preview. An existing shared working document uses the collaborative patch path above; the Markdown stream tools do not accept HTML. When shared-stream tools are unavailable, explicitly describe the independent-draft behavior to the user.

1. For a new artifact, reserve it with `mcp__artifacts__artifact_draft_create`; for a revision, read the existing artifact with `mcp__artifacts__artifact_read` and keep its current version ID.
2. Call `mcp__artifacts__artifact_draft_begin` with that artifact and `expected_version_id` (null for a new artifact). Keep the returned `draft_id` and `durable_offset`.
3. Submit a complete section or another useful chunk with `mcp__artifacts__artifact_draft_append`. Copy the last acknowledged `durable_offset` into `offset`; keep the same draft ID and use a distinct operation ID. The service computes the UTF-8 byte count and hash. Wait for the committed acknowledgement before drafting the next chunk. Several successful append calls provide visible, persisted progress.
4. After every intended section is acknowledged, call `mcp__artifacts__artifact_draft_finish` with the same draft ID and copy the last `durable_offset` into `expected_offset`. The service verifies the saved source and publishes one immutable version. Return its confirmed link.

These are Tick Loop's model-visible names; use the installed discovered tools. Each call contains complete JSON arguments and follows the ordinary approval path. Only approved chunks are sent; ordinary response text and thinking are not draft content. A dispatched call whose result is unknown must be checked with `mcp__artifacts__artifact_operation` using its operation ID. Do not resend it or advance using a guessed offset. Resolve a conflict by reading the draft and published state before a new operation. An unfinished draft preserves the previous published version; use `mcp__artifacts__artifact_draft_abort` only when cancellation is intended. Markdown exposes durable source to its owner, while HTML exposes progress until complete publication.
